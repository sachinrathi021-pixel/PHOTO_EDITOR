1. Phase 1 Recap and Phase 2 Overview

Phase 1 implemented the core image editor with custom stackType and queueType, eight image operations, full-snapshot undo/redo, a FIFO processing pipeline, and iterative bucket fill (both stack-based DFS and queue-based BFS). All 163 Phase 1 tests pass.

Phase 2 extends the system with five major features:

  1. Memory-aware compact history — replaces full-image snapshots with operation-specific records
  2. Brightness coalescing — merges consecutive brightness adjustments
  3. Priority scheduling — adds a priorityQueueType and toggleable scheduling modes
  4. Batch operations — amortised multi-element push/pop/add/delete
  5. Experimental evaluation — four benchmark experiments with analysis

2. Data Structures

2.1 stackType<Type> — Enhancements

New Phase 2 methods:

  • pushBatch(items[], n) — single capacity check via growTo(), then block-copies n elements. Avoids n separate grow checks.
  • popBatch(n) — decrements count in one step (clamps to stack size).
  • removeBottom() — shifts all elements left by one (O(n)), used for memory-budget eviction of the oldest history record.

2.2 queueType<Type> — Enhancements

  • addQueueBatch(items[], n) — one grow check, inserts all n items across the circular boundary.
  • deleteQueueBatch(n) — advances frontIdx by n modulo capacity in one step.

2.3 priorityQueueType<Type> — New

An ordered dynamic array where data[0] is the highest-priority element (smallest .priority value). Insertion shifts elements to maintain sorted order (O(n) insertion, O(1) front/delete). Ties are broken by arrival order (FIFO): a new element with the same priority is placed after all existing elements of that priority. The array doubles when full.

OperationTimeSpace
addQueue (insert)O(n) — shifts to maintain orderO(n) total
front / deleteQueueO(1) / O(n) — shift after remove—
peekAt(i)O(1)—
Design decision: An ordered array was chosen over a binary heap because (a) it is closer to the data structures taught in the course, (b) it supports simple peekAt() traversal for the Inspector and finalization barriers, and (c) with typical queue sizes of 10–50 jobs, the O(n) insertion cost is negligible.

3. Memory-Aware Compact History

3.1 Record Design

Instead of storing a full copy of the image for every undo record, HistoryRecord stores only the data needed to reverse each specific operation:

OperationUndo Data StoredEstimated Size
RotateAngle only (inverse rotation computed)~100 bytes (struct only)
FlipDirection only (flip is self-inverse)~100 bytes
BrightnessDelta + full pre-op pixel array (for clamping)W×H×3 + overhead
CropCrop coordinates + full pre-crop imageoldW×oldH×3 + overhead
Bucket FillChanged pixel coordinates + original valueschanged × (sizeof Point + sizeof Pixel)
Grayscale / Blur / ResizeFull previous imageW×H×3 + overhead

Key insight: Rotate and flip records are essentially free — they store no pixel data at all. Bucket fill records are proportional to the number of changed pixels, not the total image size.

3.2 Memory Budgeting

A configurable memoryBudget (in bytes) limits total undo+redo memory. Each record's estimatedBytes is tracked. When the budget is exceeded after recording a new operation, the oldest undo record is evicted via stackType::removeBottom(). Setting budget to 0 disables the limit.

3.3 Undo/Redo Mechanics

Undo creates a "redo record" that captures the current image state before reverting, then pushes it to the redo stack. For rotate/flip, the redo simply re-applies the same operation. For pixel-based operations, the redo record stores the post-operation image so it can be restored exactly. This ensures perfect round-trip fidelity even after clamping.

4. Brightness Coalescing

When a brightness operation is recorded and the top of the undo stack is already a brightness record, the two are merged: the deltas are summed, and the older record's saved pixels (the pre-chain originals) are kept. The new record is discarded without increasing memory.

Why this is correct: The saved pixels in the coalesced record represent the image before the entire chain of brightness adjustments. Undoing restores those exact pixels, reversing the cumulative delta in one step regardless of clamping.

Interruption: Any non-brightness operation breaks the chain. Subsequent brightness operations start a new chain.

Tested: Three consecutive brightness(+10, +20, +5) produce one record with effective delta 35. Undo restores the exact original. Clipping at 255 is handled correctly because the original pixel values are preserved.

5. Priority Scheduling

5.1 Design

The user can toggle between FIFO mode (uses queueType) and Priority mode (uses priorityQueueType). Priority levels:

PriorityValueOperations
Highest1Undo, Redo
High2Blur, Bucket Fill
Medium3Resize
Low (Finalization)4Save, Export

Within the same priority level, FIFO ordering is preserved (the priority queue's insertion logic places new elements after existing elements of equal priority).

5.2 Finalization Barriers

Save and Export jobs act as natural barriers: they have the lowest priority (4), so all higher-priority jobs submitted before them are processed first. Jobs submitted after a finalization job receive higher sequence numbers and are handled after the barrier completes.

6. Batch Operations

Batch methods perform a single capacity check and one possible growth/reallocation, then insert or remove multiple elements. This avoids redundant bounds checks and potential multiple reallocations.

MethodSingle-call equivalentBenefit
pushBatch(items, n)n × push()1 grow check vs n
popBatch(n)n × pop()1 decrement vs n
addQueueBatch(items, n)n × addQueue()1 grow check + unwrap vs n
deleteQueueBatch(n)n × deleteQueue()1 modular advance vs n

7. Experimental Evaluation

Experiment A — Stack vs Queue Bucket Fill

Uniform white images filled with a single colour, averaged over 3 runs per size.

Image SizeStack Time (ms)Queue Time (ms)Stack Max SizeQueue Max SizeInsertions (both)
512×51210.0210.09130,817512262,144
1024×102435.5441.90523,7771,0241,048,576
2048×2048129.26131.952,096,1292,0484,194,304

Analysis:

  • Both versions perform the same number of insertions (exactly one per pixel), confirming no pixel is revisited.
  • Execution time is nearly identical because the dominant cost is pixel access and memory allocation, not the push/pop operations.
  • Peak memory differs dramatically: The stack-based (DFS) version reaches ~N/2 elements on a uniform N×N image because DFS pushes an entire row of neighbours before backtracking. The queue-based (BFS) version maintains a wavefront of width ≈ N, using ~255× less memory than the stack version.
  • Conclusion: Queue-based fill is strongly preferred for memory efficiency. On a 2048×2048 image, the stack needs 2M entries (~16 MB) while the queue needs only 2K entries (~16 KB).

Experiment B — Memory-Aware History

100×100 image with repeated brightness operations under a 5 MB budget.

OperationsUndo Stack SizeMemory UsedApply Time (ms)Undo All Time (ms)

Analysis:

  • All brightness operations coalesce into a single record — the undo stack always has exactly 1 entry regardless of how many brightness operations are applied.
  • Memory usage is constant at ~30 KB (the 100×100 pre-operation pixel array + struct overhead), well within the 5 MB budget.
  • Undo is instantaneous because it restores one record containing the original pixels.
  • Conclusion: Coalescing is extremely effective for repeated homogeneous operations — it reduces both memory and undo time from O(n) to O(1) in the number of operations.

Experiment C — FIFO vs Priority Scheduling

36 mixed jobs (8 resize, 12 blur, 5 fill, 4 undo, 1 save, 1 export, 5 more resize, 4 more blur).

ModeTotal Time (ms)Execution Order (first 5)
FIFO7.02Resize → Resize → ... → Blur → ...
Priority10.12Undo → Undo → ... → Blur → ...

Analysis:

  • FIFO processes jobs in submission order. Undo/redo operations run late (jobs 22–25), after all 16 resizes and blurs.
  • Priority promotes undo/redo (priority 1) to the front, processes all blurs/fills (priority 2) next, then resizes (priority 3), and finally save/export (priority 4).
  • Priority mode is slightly slower overall due to the O(n) insertion cost of the ordered-array priority queue. However, the latency of urgent operations (undo/redo) is much lower because they run immediately.
  • Conclusion: Priority scheduling trades marginal throughput for better responsiveness to high-priority operations like undo. The insertion overhead is negligible for typical workloads (<50 jobs).

Experiment D — Single vs Batched Operations

Integer elements inserted/removed from stack and queue.

StructureOperationNSingle (ms)Batch (ms)Speedup
Stackpush1,000<1<1—

Stackpush100,0001.00<1~∞

Analysis:

  • At small sizes (1K–10K), the difference is negligible because the per-call overhead of bounds checking is tiny.
  • At 100K elements, batch queue add is 2.5× faster because the single-call version may trigger multiple reallocations (each doubling requires copying all existing elements), while the batch version does one growTo() call that allocates the final size directly.
  • Stack push batch at 100K shows the biggest improvement: single-call triggers log₂(100000/16) ≈ 13 doublings, each copying progressively more data. Batch does one allocation.
  • Pop/delete operations are always O(1) per element and show no significant difference.
  • Conclusion: Batch operations are most beneficial for insertion-heavy workloads exceeding 10K elements, particularly when the initial capacity is small and many reallocations would otherwise occur.
